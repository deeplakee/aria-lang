# mimalloc 分配器引入评估与静态集成(2026-09-27)

> 问题:是否把 mimalloc 引入为 aria 的内存分配器,以及能否静态链接。最终状态(2026-09-27
> 拍板,见 §11):mimalloc v3.5.3 vendored 于 `external/mimalloc`,MI_OVERRIDE=OFF,GC 层三个
> 分配原语显式路由,**默认 ON**(`ARIA_USE_MIMALLOC=OFF` 退回 std::malloc 家族);jemalloc 经
> 同日对照评估后弃用出库(§7)。本文档是评估与集成的唯一落库物,复测命令见 §6。

## 结论速览

- **静态接管进程 malloc 在 macOS 26 上不可用**,且与编译器、mimalloc 大版本、接管机制
  (interpose / malloc zone)均无关:AppleClang 21 与 Homebrew LLVM 22.1.8、v3.5.3 与 v2.1.7、
  interpose 与 zone-only 四种组合全部崩溃(§2)。崩溃可用与 aria 无关的 20 行复现器钉死(§2.1)。
- **解法 = 不接管**:MI_OVERRIDE=OFF,mimalloc 作普通静态 C 库,GC::allocate/reallocate/deallocate
  显式调 `mi_malloc/mi_free`(§3)。指针两端同源,无跨镜像问题,静态链接天然安全,跨平台成立。
- **正确性**:注入态与路由态各跑全量 ctest,两配置均 1198/1198 全绿;路由规模经堆统计核实
  (binary_trees 单次 507.9 MiB 走 mimalloc)。
- **性能结构分化(47 行全量,两臂各两遍,负载段口径,中位 1.000 / 均值 0.949)**:
  - 分配密集行**快 18%~41%**:list_slice -41%、closure_creation -36%、destructure_assign -35%、
    binary_trees -22%(lang-bench-notes 钦定的 GC / 对象分配观测行);
  - 调用路径的小对象模式**慢 5%~17%**:closure_upvalue +17%、scope_locals +11%、plain_call +7%、
    call_hook +9%、operator_overload +8%;
  - 纯计算负载(算术 / mandelbrot / sieve / fasta)中性。
  - 与第一轮动态注入相比,赢的行赢面更大、输的行输面也更大(§4.2)。
- **内存**:word_count 峰值 RSS 116 -> 138 MB(+19%),binary_trees +8%,常驻 +0.5 MB(无 dylib,
  纯静态);启动 +0.08 ms(无包装伪影,裸进程直测)。

## 1. 环境

Apple M4,macOS 26.6.1;aria = main@3e7d66a 原样 Release(thin LTO,-O3 -DNDEBUG,GC 开发期即开)。
编译器两套:AppleClang 21(`/usr/bin/c++`,项目默认)与 Homebrew LLVM 22.1.8
(`/opt/homebrew/opt/llvm`,自带静态 libc++.a / libc++abi.a / libunwind.a)。mimalloc v3.5.3 主测,
v2.1.7 回归对照。基准驱动 `bench/lang/lang_bench.py --langs=`(纯 aria 全量 47 行,预热 1 + 5 轮,
负载段 = 脚本内 `clock()` 自测),两臂各跑两遍取平均;同臂遍间差异中位 0.3%~0.5%;<5% 的跨配置
差异不当结论(测量纪律见 `.claude/reference/bench/lang-bench-notes.md`)。

## 2. 静态接管:四种组合全崩(不可用)

第一轮已证 AppleClang + v3.5.3/v2.1.7 的静态 interpose override 在 Release(-O2/-O3)下必崩;
本轮换 Homebrew LLVM 22.1.8 重测 interpose 静态,同样 8/8 崩——**编译器不是变量**。问题在
dyld/libc++ dylib 层:`std::filesystem::current_path` 返回对象由 libc++ dylib 侧构造(系统堆分配),
主镜像内联析构释放时符号落到 mimalloc 的 override(`vfree -> mi_free`),mi_free 对异域指针无护栏。

### 2.1 最小复现器(与 aria 无关)

```cpp
// c++ -O3 -std=c++23 -include mach-o/dyld.h repro.cpp libmimalloc.a && ./a.out
#include <filesystem>
#include <string>
#include <vector>
#include <expected>
namespace fsn = std::filesystem;
std::expected<std::string, int> current_dir() {
    std::error_code ec;
    const auto p = fsn::current_path(ec);   // dylib 侧构造 path(分配在 dylib 侧)
    if (ec) return std::unexpected(1);
    return p.string();                       // 本 TU 内联析构 -> free -> mi_free(异域指针)
}
int main() {
    std::vector<std::string> roots;
    roots.push_back(current_dir().value_or(""));
    return roots.empty() ? 1 : 0;
}
```

### 2.2 zone-only 变体同样不可用

mimalloc 在 macOS 另有一条「只注册 malloc zone、不 interpose」的接管路径
(`MI_OSX_INTERPOSE=OFF`,构造器里 register + 摘除原默认 zone 使己方成为默认)。实测:

| 构建 | 纯 C 程序(主镜像内 malloc/free) | C++ 复现器(std::filesystem) |
| --- | --- | --- |
| v3.5.3 zone-only 静态 | 5/5 通过 | 8/8 崩(崩在 mi_free 的 abandoned-page 回收) |
| v2.1.7 zone-only 静态 | - | 4/4 崩(崩在 operator delete -> free 链) |

zone 的 free 回调本有归属护栏(`mi_cfree` 只放自有指针),纯主镜像程序一致;但 C++ 程序的
分配流穿过 libc++ dylib 后仍崩。**结论:凡「接管进程 malloc」的静态形态在本机 macOS 26 上
都不可用**,不因编译器 / 版本 / 机制而异。

(第三条路是 Homebrew LLVM 自带静态 libc++ + libc++abi + libunwind 全静态链接运行时,使全部
C++ 分配流收进主镜像——被否:给整个程序换 C++ 运行时只为一个分配器,爆炸半径远超收益。)

## 3. 最终集成:MI_OVERRIDE=OFF + GC 层显式路由

aria 是 GC 拥有对象堆的解释器:全部热路径分配(对象、GC scratch、驻留池)都经
`GC::allocate / reallocate / deallocate` 出入,指针两端同源。因此不需要接管进程 malloc——
把这三个原语显式路由到 mimalloc 即可,其余(编译期 vector / String 等)留在系统分配器:

- `src/memory/GC.hpp`:`aria::detail::mem::raw_alloc / raw_free` 后端二选一
  (`ARIA_USE_MIMALLOC` 宏切换 `mi_malloc/mi_free` 与 `::operator new/delete(nothrow)`),
  三个模板函数改调 helper,逻辑与记账(`bytes_allocated_`)不变;
- `CMakeLists.txt`:`ARIA_USE_MIMALLOC` 选项(默认 OFF)→ `MI_OVERRIDE=OFF` +
  仅静态库 + `target_compile_definitions/link_libraries(aria_core PUBLIC ...)`;
- mimalloc v3.5.3 vendored 于 `external/mimalloc`(同 isocline 先例,入库)。

对齐:mi_malloc 的保证对齐 = 16 B(64 位),与 `::operator new` 的
`__STDCPP_DEFAULT_NEW_ALIGNMENT__` 一致;GC 对象均为平凡对齐的 struct,无超对齐需求。

### 4.2 分组解读与两轮对照

- **分配密集行全数大涨且比注入轮更大**:list_slice -41%(注入轮 -32%)、closure_creation -36%、
  destructure_assign -35%、forin_destructure -32%、destructure_slice -28%、call_varargs -24%、
  map_methods -24%、binary_trees -22%(注入轮 -14%)。静态直调(无 dylib PLT 与 interpose
  中转)让快路径更直接。
- **调用路径的小对象模式回退也比注入轮更大**:closure_upvalue +17%(注入轮 +11%)、
  scope_locals +11%、call_hook +9%、operator_overload +8%、plain_call +7%、
  call_default_params +6%、method_dispatch +5%。该形态(每次调用单个小对象与计算紧密交错
  生灭)是 mimalloc 相对系统 nano malloc 的内在弱项,静去了中转后被更完整地暴露。
- **exception_deep_unwind 翻转**(-31% -> +2%):该行在注入轮的红利大部分来自编译器侧 /
  非对象分配也被接管,路由态只看 GC 对象后红利消失。其余纯计算行保持中性。
- **全表分布**:13 行 >=5% 变快,7 行 >=5% 变慢,27 行在 +-5% 内;中位 1.000,均值 0.949
  (均值被深尾赢面拉低)。

## 5. 结论

1. **静态接管不可行,已证伪穷尽**:interpose / zone-only 两机制 × v2/v3 两版本 ×
   AppleClang/Homebrew 两工具链,八种静态接管组合全数崩溃或有系统性风险;macOS 上
   mimalloc 的可用静态形态只有「不接管、显式调用」。
2. **显式路由集成已落地**(`ARIA_USE_MIMALLOC`,默认 OFF):正确性 1198/1198 全绿,
   分配密集负载赢 18%~41%(binary_trees -22% 直接收复对 CPython 的部分差距),代价是
   调用路径 5%~17% 回退与大 churn 负载的峰值 RSS(+19%)。
3. **默认是否翻 ON 留待拍板**。取舍:aria 的卖点在派发速度(method_dispatch / plain_call
   一族),mimalloc 在这族上是净负;但真实负载(binary_trees 等)普遍分配密集,赢面实在。
   倾向维持 OFF 作为可选开关,待 GC / 对象布局优化主线启动时按 §6 复测再定;
   若要翻 ON,建议同步评估调用路径回退的解释器侧吸收手段(如 bound method / upvalue 的
   缓存或池化,现 bound 缓存已裁撤,重开需另立论证)。

## 6. 复现步骤

```sh

cmake -S . -B build/rel      -DCMAKE_BUILD_TYPE=Release
cmake -S . -B build/rel-nomi -DCMAKE_BUILD_TYPE=Release -DARIA_USE_MIMALLOC=OFF
cmake --build build/rel      -j4
cmake --build build/rel-nomi -j4

# 正确性(两树各自全量)

```

### 7.3 选型含义

两开关(默认均 OFF)的画像:**mimalloc = 高方差后端**(分配密集负载上限高,调用路径下限低);
**jemalloc = 低方差后端**(处处小赚或打平,例外是深 unwind)。aria 若要在发布配置里开一个,
取决于优化立场:追真实负载吞吐(binary_trees 族)选 mimalloc 并想办法吸收调用路径回退;
求全负载无短板选 jemalloc,代价是放弃分配密集行的最深红利。维持默认 OFF、按需开关是当前
最稳的落点。

## 10. std::malloc 家族统一 + 原生 realloc(同日第四轮)

应用户命题把三后端统一到原生 realloc:default 后端从 `::operator new/delete` 切到
`std::malloc/std::free`,GC::reallocate 的「模拟 realloc」(alloc+memcpy+free)换成后端原生
realloc(`std::realloc` / `mi_realloc` / `je_realloc`,同一三路 #if 收口)。动机:aria 此前
从未吃过原生 realloc 的红利——所有可增长缓冲(List 元素数组/值栈/GC scratch,经
Buffer::reserve 倍增)都在交「整块 memcpy + 双份瞬态」的税;HashTable rehash 语义上不可
realloc(探针序列须重算),不在此列。改动 ~30 行 + 三处注释契约同步(Buffer::reserve 的
「可能原地扩展也可能搬迁」、ObjMovement::grow_stack_ 的基址重绑分支由「防御性保留」转为
活路径)。前置约束:realloc 三口必须同族,new 的块喂 realloc 是 UB,故 default 后端一并切
malloc 家族(GC 内存是裸字节 + trivially-copyable 容器契约,安全;std::malloc 的基本对齐
保证与 nothrow new 相同)。

**正确性**:三树(default/mimalloc/jemalloc,均重建于本改动之上)各跑全量 ctest,均
1198/1198 全绿,含 GC 压力语料与值栈扩容重绑路径。

### 10.4 RSS:原生 realloc 的红利取决于后端的大块扩展能力

| 负载 | default | mimalloc | jemalloc |
| --- | ---: | ---: | ---: |
| word_count 峰值 RSS | 115.9 -> **101.0 MB(-12.9%)** | 138 -> 137.5(不变) | ~123 -> **106.9 MB(-13%)** |
| binary_trees 峰值 RSS | 5.5(不变) | 5.9 -> 6.0 | 7.0 -> 6.3~7.0 |

三后端各测 3 遍,读数逐位稳定。解释:模拟 realloc 的瞬态双份(旧块+新块共存)能否消除,
取决于后端 realloc 对大块的原地扩展能力——系统 malloc(macOS libmalloc)与 jemalloc
(rallocx)都支持大块原地扩展,双双 -13%;mimalloc 的 mi_realloc 对大块内部仍是「新分配 +
拷贝 + 释放」,瞬态仍在,红利不出现。这与 §10.3 的时耗面互为印证:mi 在 word_count /
fasta 的 +3% 与其 137.5 MB 的 RSS 同源——mimalloc 的优势在小对象 churn(§10.3 的深赢行),
大块 realloc 形态反而让系统分配器占先。

### 10.5 判决

**保留本改动**。三后端分配契约统一、缓冲行 -3%~-7% 实拿、workloads 组全员小赚或
持平、default / je 的 RSS 瞬态消除、派发行无机制性代价;布局噪声是构建彩票,不构成回退
依据。分配器画像在 realloc 基座上重述:**mimalloc = 高方差后端**(高分配深赢 + 派发惩罚 +
大块 realloc 不受益),**jemalloc = 低方差后端**(平坦 + 深 unwind 弱项),default(系统
malloc 家族)= 缓冲形态与 RSS 的隐性赢家。GC 池(§9)若立项,原生 realloc 也是它的前置
基建(缓冲路径可直接受益)。

第一轮(动态注入)测量:基线二进制 + `DYLD_INSERT_LIBRARIES=libmimalloc.3.dylib`,注入态
ctest 1198 全绿;47 行中位 0.991 / 均值 0.950,分配密集行 -14%~-32%,调用路径 +5%~+11%,
详细表已由本轮表格取代,数字以 §4 路由态为准。

## 11. 落地决定(2026-09-27 收口)

综合 §4 / §7 的路由对照、§8 的真实形状校准与 §10 的 realloc 基座三臂,拍板如下:

- **mimalloc 为唯一第三方分配器依赖,默认 ON**:`ARIA_USE_MIMALLOC` 默认翻 ON,
  `external/mimalloc` 入库;OFF 是零开销逃生门(退回 std::malloc 家族,ctest 把关)。
  raw_alloc/raw_realloc/raw_free 收口(b8f97ee)正是本形态的前置。
- **jemalloc 弃用出库**:无 Windows 端口(与三平台目标冲突)、赢面浅(最好的 binary_trees
  -5.8% 对 mimalloc -20%)、exception_deep_unwind +28% 结构性弱项、autotools 集成脆。
  对照数据保留在 §7 作档案;`external/jemalloc` 与 CMake 接线移除。
- **默认 ON 明着接受的代价**:派发家族微基准 method_dispatch +5.0% / operator_overload
  +7.4%(§10.3);字符串 churn 峰值 RSS 101.0 -> 137.5 MB(§10.4,mi_realloc 大块不原地
  扩展);启动 +0.5 MB。理由:workloads(离体感最近的一组)中位 0.982、分配密集的真实程序
  深赢,且默认 ON 让 ON 路径活在日常构建;§9 的壳池若立项,后端将退出对象壳热路径,这批
  代价随之收缩。
- **待补验证**:本评估全部在 macOS 完成;落地后 Linux 至少冒烟一遍、Windows 确认 vendored
  构建可用,再视结果回看默认值。
